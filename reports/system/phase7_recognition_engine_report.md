# AutoRoll Phase 7 — Production Face Enrollment & Recognition Engine Audit Report

## Executive Summary

The production AutoRoll face enrollment and recognition engine has been successfully implemented, verified, and integrated under `backend/app/`. The system introduces a unified model abstraction interface (`FaceRecognitionModel`), supporting dynamic model switching between the ONNX baseline (`pretrained`) and fine-tuned PyTorch checkpoint (`autoroll_v1`). Multi-sample face enrollment, passive anti-spoofing liveness verification, normalized mean template aggregation, sliding-window temporal attendance confirmation, and real-time monitoring WebSockets are fully operational with zero model weight alterations or dataset modifications.

## Model Abstraction & Dynamic Switching

The application dynamically selects recognition models using configuration setting `AUTOROLL_RECOGNITION_MODEL`:

1. **`pretrained` (ArcFace R50 ONNX Baseline):**
   - Weights Path: `models/pretrained/arcface_r50_webface_or_glint/model.onnx`
   - Validated Decision Threshold: `0.0440`
   - Embedding Dimension: 512
   - Execution Provider: `CUDAExecutionProvider` / `CPUExecutionProvider` via ONNX Runtime

2. **`autoroll_v1` (AutoRoll Fine-Tuned PyTorch Checkpoint):**
   - Weights Path: `models/trained/autoroll_arcface_v1/epoch_001.pt`
   - Validated Decision Threshold: `0.0540`
   - Embedding Dimension: 512
   - Execution Provider: PyTorch (`cuda` / `cpu`)

### Model Versioning Safety & Compatibility Guard
Every face template stored in the database records `model_id`, `model_version`, `embedding_dimension`, and `sample_count`. Comparing an observation embedding against templates generated by an incompatible model triggers an explicit `INCOMPATIBLE_MODEL_TEMPLATE` rejection.

## Production Workflows

### 1. Student Enrollment Workflow
- **Session Init:** `POST /api/v1/enrollment/start` creates session for student code and name.
- **Sample Capture (5–10 samples):** `POST /api/v1/enrollment/{session_id}/frame` filters frame quality, verifies anti-spoofing liveness, aligns 112×112 face chip, extracts ArcFace 512-dim embedding, applies L2 normalization, and logs rejection reasons (`no_face`, `multiple_faces`, `poor_quality`, `spoof_detected`).
- **Template Aggregation:** `POST /api/v1/enrollment/{session_id}/complete` computes normalized mean vector:
  $$\mathbf{v}_{\text{mean}} = \frac{1}{N} \sum_{i=1}^N \mathbf{v}_i, \quad \mathbf{v}_{\text{template}} = \frac{\mathbf{v}_{\text{mean}}}{\|\mathbf{v}_{\text{mean}}\|_2}$$
  Persists template in DB with `model_id`, `model_version`, `embedding_dimension=512`, `sample_count=N`.

### 2. Liveness & Temporal Attendance Confirmation
Attendance requires **all** of the following conditions:
1. Face detected (confidence $\ge 0.50$).
2. Face quality acceptable (`is_quality_ok == True`).
3. Liveness passed (`combined_liveness_score >= 0.90`).
4. Template model matched (`template.model_id == recognizer.model_id`).
5. Cosine similarity $\ge$ model threshold (`0.0440` or `0.0540`).
6. **Temporal Confirmation:** Same identity observed $\ge 3$ times within $1500\text{ ms}$.

Attendance decisions emit standard codes: `PRESENT`, `PENDING_TEMPORAL`, `REJECTED_SPOOF`, `LOW_QUALITY`, `INSUFFICIENT_CONFIDENCE`, `INCOMPATIBLE_MODEL_TEMPLATE`.

## Security & Privacy Enforcement

1. **Zero Raw Embeddings over Wire:** WebSockets and REST responses sanitize and exclude raw 512-dim embedding vectors.
2. **Transient Frame Processing:** Input images are processed strictly in RAM and discarded immediately.
3. **Identifier Scoping:** Internal system operations use UUID student IDs rather than personally identifiable information.

---

## Known Limitations & Future Scale Path

1. **Database Search:** Current database template matching uses linear cosine comparison; for scaling beyond 100,000 enrolled students, integration of an HNSW vector index (e.g. pgvector or FAISS) is recommended.
2. **Distributed Processing:** Pipeline modules are bounded behind service interfaces, ready for worker-node scaling without structural refactoring.
